# Proposal: Option 1 — DB/Bundles as the Source of Truth for Equipment UI Metadata (No Repo Writes)

**Spec and tickets:** The authoritative spec for this feature is **docs/plans/specs/equipment-ui-metadata-db-bundles-spec.md**. Implementation is done via **docs/plans/tickets/** tickets 01–09 (01 = plan review vs codebase; 02–09 = implementation steps). Follow the spec and one ticket at a time per claude-workflow-opt.md.

## Executive Summary

We currently have a split-brain workflow for equipment templates:

- The Admin UI (deployed on Vercel) can reliably write template rows to the database.
- The Admin UI cannot reliably write to the repo filesystem on Vercel, so it cannot update `apps/web/public/assets/items/**/manifest.json`.
- The system currently treats the database as an authoring mirror and exported bundles as runtime truth, but manifests are a leftover “local filesystem authored” concept.

Option 1 resolves this by making the database + exported bundle the single canonical source of truth for all template metadata (including UI metadata) and removing the need for any runtime writes to the repository filesystem. This aligns directly with the existing Admin UI architecture defined in `admin-ui.md`:

- Runtime behavior uses exported JSON bundles (static artifacts)
- Database is an authoring mirror
- Publishing creates immutable versions for rollback

This proposal outlines the concrete implementation changes to fully adopt Option 1 for equipment template UI metadata, while keeping compatibility with the current MVP.

---

## Current System (as implemented)

### Template authoring and publishing

- Admin UI lives in `apps/web` under `/admin/*`.
- Templates are stored as rows in Supabase Postgres:
  - `GameDataBundle`
  - `EquipmentTemplate`
  - `ActionTemplate`
  - (future) `SpellTemplate`
- Publishing workflow:
  - validate templates
  - export bundle JSON to Supabase Storage
  - mark bundle `isActive = true`
  - runtime loads active bundle at server startup and caches it

### Equipment assets and manifests (local vs Vercel)

`admin-ui.md` section 2.3 describes the manifest workflow:

- Create template:
  - always writes DB row
  - optionally writes `apps/web/public/assets/items/{raritySlug}/{key}/manifest.json` if filesystem is writable (local dev)
  - on Vercel, filesystem is read-only, so manifest creation is skipped
- Update template:
  - only updates DB row
  - does NOT update manifest

Result: DB templates can change, but manifests drift unless manually edited in repo or re-seeded locally and committed.

### Important current fact

Inventory UI does not currently read per-item manifests at runtime. It renders placeholder icons and does not fetch `/assets/items/**/manifest.json`.

This means we can safely change the manifest strategy without breaking current gameplay UI.

---

## The Problem We Are Solving

We want Admin UI to be the authoritative tool for authoring:

- Equipment templates (stats, rarity, behavior)
- UI metadata (display name, icon references, later drag/drop images)

But we cannot update repo filesystem from Vercel, so “manifest files in git” cannot be kept in sync.

We need a source-of-truth architecture where:

1) Admin UI edits persist reliably
2) Those edits propagate through the game via the published bundle system
3) Repo files are not required to stay in sync to keep the game functional

---

## Proposed Change (Option 1)

### High-level shift

Stop treating `public/assets/items/**/manifest.json` as a required data source.

Instead:

- Store UI metadata on `EquipmentTemplate` (as structured data)
- Include UI metadata in the published bundle artifact
- Provide icon resolution via:
  - deterministic local paths (early phase), or
  - Supabase Storage paths (future phase), or
  - server-side mapping to avoid client complexity

Manifests become one of:
- Deprecated entirely (preferred)
- Optional compatibility artifacts (generated later by script if we want them for organization)

---

## Design Goals

1) Single source of truth:
   - Equipment template = canonical data including UI metadata
   - Published bundle = canonical runtime artifact
2) No runtime repo writes required
3) Keep current publishing + rollback semantics
4) Keep UI implementation simple (avoid N+1 manifest fetch)
5) Make future icon uploads (drag/drop) straightforward

## Proposed Data Model Changes

### Add / formalize UI metadata in EquipmentTemplate

In `admin-ui.md` EquipmentTemplate editor already includes a section:

- UI metadata: ui (JSON)

We should formalize what belongs there, and ensure it is not duplicated in manifests.

Recommended UI metadata fields:

- `displayName` (string)
- `shortName` (string, optional)
- `description` (string, optional)
- `icon` (object)
  - `source` (enum: `LOCAL_PUBLIC` | `SUPABASE_STORAGE`)
  - `path` (string: relative path or storage key)
  - `variant` (optional: `small`, `large`, etc.)
- `rarityFrameKey` (string, optional)
- `sortOrder` (number, optional)
- `tags` (string[], optional)

Example shape (illustrative only; define a stable schema and validate):

```json
{
  "ui": {
    "displayName": "Iron Sword",
    "icon": {
      "source": "LOCAL_PUBLIC",
      "path": "/assets/items/common/iron_sword/icon.png"
    },
    "sortOrder": 10
  }
}
```

### Add a stable template key reference to equipment instances

If your equipment instances do not already retain a direct `templateKey`, add it (or ensure there is a consistent join strategy).

- Equipment instance needs to be able to map to its template (via key or templateId)
- This enables server-side enrichment and avoids client guessing

## Proposed Workflow Changes

### Editing templates

No change to the high-level process:

- Admin UI edits EquipmentTemplate rows
- Validation runs on save and on publish

But we explicitly remove all filesystem side-effects as part of “template save.”

Specifically, the Admin UI API should no longer attempt:

- creating asset folders
- writing manifest.json

Instead, it only updates database rows.

### Publishing bundles

Publishing already exports canonical JSON artifacts to Supabase Storage.

Update the export pipeline to guarantee:

- EquipmentTemplate export includes `ui` metadata
- A published bundle is always self-contained enough to render inventory UI icons (once wired)

Publishing remains immutable, with rollback via `isActive`.

## Runtime Consumption Changes (Client + Server)

There are two viable runtime consumption strategies. Both avoid reading per-item manifests.

### Strategy A (Preferred): Server-side enrichment for inventory endpoints

When serving equipment instances via `/api/equipment`:

- Join instances to templates (by templateKey/templateId)
- Attach UI fields to each returned item:
  - `displayName` (from template ui.displayName or template name)
  - `iconUrl` (resolved based on ui.icon.source + ui.icon.path)
  - `rarityFrameKey` (optional)

Result: UI renders items without additional fetches or path logic.

Example output fields on each equipment item:

```json
{
  "id": "...",
  "templateKey": "iron_sword",
  "rarity": "COMMON",
  "rolledMods": [],
  "displayName": "Iron Sword",
  "iconUrl": "/assets/items/common/iron_sword/icon.png"
}
```

Benefits:
- UI is dead simple
- No N+1 fetch of templates or manifests
- Works regardless of whether icons live in local public assets or Supabase Storage
- Allows caching on the API layer if needed

### Strategy B: Client loads the active bundle once and resolves template UI locally

If we want fewer server joins:

- Client loads active bundle JSON once (or a subset)
- Client maps equipment instance -> template UI locally

This is viable but adds client-side data plumbing and versioning concerns.

Given current architecture (server-authoritative simulation and APIs), Strategy A is recommended for now.

## Asset Strategy Options Under Option 1

Option 1 decouples “where the icon lives” from “how templates reference it.” We can phase this in:

### Phase 1: Local public assets (fastest)

- Icons exist in repo under `apps/web/public/assets/items/**`
- Templates store icon path as `/assets/items/.../icon.png`
- No manifests required
- Admin UI does not upload images yet; icons are pre-seeded by devs in repo

This is essentially “Option 1 without drag/drop,” but still fixes the Vercel write issue.

### Phase 2: Supabase Storage icons (future-friendly)

- Admin UI allows uploading an icon to Supabase Storage
- Store the storage key/path in `EquipmentTemplate.ui.icon.path`
- `iconUrl` resolved from Supabase Storage public URL (or signed URLs if desired)

This enables drag/drop image uploads later without changing the template workflow again.

## Changes to Admin UI

### 1) Remove filesystem side-effects from EquipmentTemplate create

In `admin-ui.md` 2.3, the system currently tries to create a folder + manifest when writable.

Under Option 1, the API should instead:

- Always update DB
- Return fields indicating whether icon metadata is complete, e.g.:
  - `ui.icon.path` exists or not
  - `ui.displayName` exists or not

Recommended “health” fields for the editor:

- `uiStatus`: `OK | MISSING_ICON | MISSING_DISPLAY_NAME | INVALID_ICON_PATH`
- Validation errors surfaced inline

### 2) Make UI metadata editor first-class

Ensure `/admin/equipment-templates/:key` supports:

- UI Display Name
- Icon Source selector:
  - LOCAL_PUBLIC
  - SUPABASE_STORAGE
- Icon Path input:
  - If LOCAL_PUBLIC: requires a path beginning with `/assets/`
  - If SUPABASE_STORAGE: requires a storage key prefix, e.g. `items/common/iron_sword/icon.png`

### 3) (Future) Upload UI icon directly

Down the line:
- Add an upload component to Admin UI
- Upload to Supabase Storage
- Auto-populate `ui.icon.path` and set source to SUPABASE_STORAGE

---

## Validation Changes

Update bundle and record-level validation to enforce UI metadata constraints:

- `ui.displayName` required (or fallback to template name if present)
- `ui.icon.source` must be a valid enum
- `ui.icon.path` required for any template that should be visible in inventory
- Optional: validate icon paths match a whitelist:
  - `/assets/items/...` for local
  - `items/...` for storage

Validation rules can be:
- strict during publish (block publish if missing)
- lenient during draft (warn but allow save)

Recommend:
- Warn on save
- Block publish if icon fields are missing for templates flagged as `PUBLISHED`

## Publishing and Bundle Format

Ensure bundle export includes full UI metadata for each template.

Example export shape for equipment template:

```json
{
  "equipmentTemplates": [
    {
      "key": "iron_sword",
      "type": "WEAPON",
      "rarity": "COMMON",
      "baseStatMods": [],
      "actions": [],
      "ui": {
        "displayName": "Iron Sword",
        "icon": {
          "source": "LOCAL_PUBLIC",
          "path": "/assets/items/common/iron_sword/icon.png"
        }
      }
    }
  ]
}
```

This bundle is now self-sufficient for UI rendering.

## Migration Plan

### Step 0: Confirm current runtime expectations

- Confirm which endpoints serve equipment inventory data (`/api/equipment`)
- Confirm how equipment instances link to templates (key vs foreign key)
- Confirm whether templates already contain a `ui` JSON column and how it’s used

### Step 1: Deprecate manifest write logic

- Remove / disable any code paths that attempt to:
  - create asset folders
  - write `manifest.json`
- Update Admin UI responses accordingly

### Step 2: Backfill UI metadata on existing templates

For the existing chestplates and weapons:
- set `ui.displayName`
- set `ui.icon.source = LOCAL_PUBLIC`
- set `ui.icon.path` to a deterministic repo asset path (even if placeholder image)

### Step 3: Update bundle export to include UI metadata

- Ensure exported JSON includes `ui`

### Step 4: Update `/api/equipment` to return iconUrl/displayName (Strategy A)

- Join instances to templates
- Resolve `iconUrl` from template ui fields
- Add `displayName` field

### Step 5: Update inventory UI to render icons

- Replace emoji placeholders with:
  - if iconUrl exists: render image
  - else fallback to emoji

### Step 6: Remove or ignore manifest usage

- Confirm no code reads manifests
- Optionally delete manifests or keep them as static placeholders until later cleanup

## Rollout and Safety

### Backwards compatibility

- During rollout, continue supporting emoji fallback in UI
- Do not require icons for all templates until ready

### Rollback strategy

- Bundle publishing already supports rollback by switching active version
- If icon metadata breaks, rollback to previous active bundle

3) Export/Publish

4) API

- Render icons if present, fallback if missing
- Keep fast, tactical UI

6) Optional future
- Implement icon upload to Supabase Storage
- Update icon.source to SUPABASE_STORAGE for uploaded assets
- No further changes needed to client if iconUrl is resolved server-side

## Tradeoffs and Why This Is Worth It

### What we lose

- The “manifest file in repo” as a human-editable source of UI metadata

### What we gain

- A single authoritative pipeline (DB authoring -> bundle -> runtime)
- No Vercel runtime write issues
- Stronger determinism and rollback safety
- Easy future extension to image upload without rewriting the system
- Cleaner separation: repo assets are static; game data is authored via Admin UI

This change aligns exactly with the Admin UI architecture direction already chosen: exported bundles are canonical runtime behavior; DB is an authoring mirror. Option 1 simply completes that design by removing the last filesystem-authoring dependency.
